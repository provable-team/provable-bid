# Concurrent development handoff

The API contract is the shared interface between Developer A (Codex: frontend/UX)
and Developer B (Claude: backend/PayPal/agents). This repository contains the buyer
frontend, architecture, generated client/types, provider interfaces, a local mock,
and contract checks. The internal personas share one platform operator and economic
recipient; public identities are not independent payout accounts. A real backend
adapter has not yet been built against this contract.

The frontend targets **v0.3.0**, merged into `main` in PRs #1 and #2. Read
[BACKEND-HANDOFF.md](BACKEND-HANDOFF.md) and [CONTRACT-CHANGES.md](CONTRACT-CHANGES.md).
The collaborator prototype has different product/payment behavior; see
[BACKEND-INTEGRATION-AUDIT.md](BACKEND-INTEGRATION-AUDIT.md).

## Start in either developer's clone

Node.js 24+ and npm 11+ are recommended. Install the lockfile exactly:

```sh
npm ci
npm run check
npm run mock
```

Mock listens on **http://127.0.0.1:4010**, loopback only, with CORS for localhost:3000
and 127.0.0.1:3000. It binds only to loopback deliberately: fixture tokens, mock
payment observations, clock controls, and mock webhook signatures provide no security
outside local development. Never deploy `apps/mock-api` to a public service. Restart
the process to clear in-memory state. It performs no external provider calls.

| Local bearer token | Identity / access |
| --- | --- |
| `buyer-demo` | Demo buyer / owns its briefs and purchases |
| `buyer-other` | Separate buyer / checks ownership failures |
| `agent-alpha` / `agent-alpha-rotated` | Same registered Neon Frame agent, separate fixture credentials |
| `agent-beta` | Paper Sun — warm editorial; text + image |
| `agent-gamma` | Lunar Ink — monochrome noir; text + image |
| `agent-guest` / `agent-guest-alt` | Two allowlisted external-test personas owned by one guest operator; no internal-run registration |
| `admin-demo` | Local grading, payment observations, time controls, refund/reconciliation |

The mock's approval URL is an informational fixture, not a payment page. Calling
`authorize` simulates approved order verification and authorization; calling an
additional purchase's `capture` simulates its approval. Captures remain pending until
an explicit admin observation. Never use `admin-demo` in the buyer frontend.

## Files and ownership

| Area | Owner | Integration promise |
| --- | --- | --- |
| `contracts/openapi.yaml` | Both; appoint A as merge owner | Only wire source of truth; communicate a contract diff before changing consumer behavior. |
| `packages/api-client/src/schema.d.ts` | Generated, neither edits manually | Regenerate and include in every contract change. |
| `packages/api-client/src/index.ts` | A | Typed openapi-fetch transport, generated exports; no payment logic. |
| `apps/mock-api/` | A during UI build | Executable fixture matching contract, not source for production security or persistence. |
| `apps/web/` | A | Brief creation, consent, approval redirect, countdowns, previews/checks, selection, purchase and payment states. |
| Future `apps/api/` and worker | B | Database transactions, ownership, durable jobs, evaluator, sandbox adapter, webhook verification and reconciliation. Use chosen runtime. |
| `packages/agent-interface/` | B | Internal adapter/evaluator boundary; external agents use the REST contract. |
| `ARCHITECTURE.md`, `PAYPAL-FLOWS.md` | Both | Frozen semantics and provider acceptance requirements. |
| `tests/contract.test.ts` and CI | Both | Examples, every operation, client compatibility and race/financial invariants. |

Two separate local clones and short feature branches avoid tool interference.
Initial tasks can proceed independently once both developers run `npm run check`.
Do not add fields to the mock alone or hand-maintain parallel DTOs in the frontend.
The local fixture must not become the production API by renaming it.

## Frontend client usage (Developer A)

`packages/api-client` exports `createApiClient`, generated `paths`/`operations`/
`components`, and convenient Competition/Submission/Payment/Purchase/Problem types.
The paths, inputs, and outputs are generated by openapi-typescript; openapi-fetch is
the typed runtime transport. The small factory is intentionally hand-written.

```ts
import { createApiClient } from '@provable/api-client';
const api = createApiClient({
  baseUrl: 'http://127.0.0.1:4010',
  token: 'buyer-demo', // Real auth token supplied by backend later.
});

// Save this key for this logical action and reuse it after a network failure.
const key = crypto.randomUUID();
const { data, error, response } = await api.POST('/v1/competitions', {
  params: { header: { 'Idempotency-Key': key } },
  body: {
    title: 'Five Minute Scenes',
    brief: 'Write a short scene with two astronauts discovering a garden on Mars.',
    bid: { currency: 'USD', amount_minor: 500 },
    submission_window_seconds: 300,
    decision_window_seconds: 300,
    requirements: [{ id: 'req_mars', description: 'A garden on Mars is discovered.' }],
    accepted_terms_version: 'sandbox-v2', // Read current config first in the actual UI.
  },
});
if (error) console.error(error.code, error.detail, response.headers.get('X-Request-Id'));
if (data) console.log(data.id, data.state);
```

UI has one API base URL setting so A can switch between mock and B's API without
component changes. Avoid naming a server secret with `NEXT_PUBLIC_`. Fetch config
before brief creation and show exact frozen commission, capped expenses, fee trigger,
and the lack of guaranteed compensation before consent. No live payout claims.

For each command, retain idempotency key until a definite response; on retry reuse
key/body. Receipt replay can be stale: poll GET after a 201/202. Do not infer paid
from successful POST, approved checkout, authorization, or a competition `closed`
state. Show pending/unknown and failed states clearly. Only offer delivery when
`delivery_unlocked` and still handle `409 DELIVERY_LOCKED` after a later refund.
No API auto-retry middleware creates fresh purchase commands. Display internal run progress
separately from the gallery; only qualified work belongs in the gallery. After early selection,
show that submissions remain open to the original deadline and additional winners cost
the original full bid. Agents can still choose whether to spend compute after that
decision. Recover purchase IDs after a refresh using `GET /v1/competitions/{id}/purchases`; it remains available
after the purchase window closes.

## Five Minute Scenes fixture sequence

With `npm run mock` running, open another terminal and run `npm run demo`. It creates
a $5 brief, opens a five-minute window, starts all three internal fixture agents,
qualifies their image + text entries, selects an early winner, simulates $5 capture,
and buys a second entry through a separate simulated checkout. It prints the gallery,
preview links, deadlines, purchase IDs, and paid-original delivery links. It also asserts
completed/500/unlocked for both purchases, distinct payment/order/capture IDs, owner-only
HTTP downloads, byte sizes, and SHA-256 hashes against each submitted artifact. Those links
require `Authorization: Bearer buyer-demo`; delivery expires after 60 seconds. The mock
server stays running with the records for frontend inspection. No external services
are called. The CLI is a contract demonstration, not a frontend application.

Use the generated client or an HTTP client. Every POST below except the webhook
requires a distinct logical `Idempotency-Key` header; GETs do not. Bodies are JSON.
The returned IDs are opaque and must be carried into later requests.

| Step | Credential | Request / expected result |
| --- | --- | --- |
| 1 | Public | `GET /v1/config`: mock, USD, fee 1000 bps, commission 1000 bps, expenses 0, payouts simulated. |
| 2 | Buyer | `POST /v1/competitions` with the OpenAPI Five Minute Scenes example: bid 500, 300s submission, 300s decision. Returns draft ID. |
| 3 | Buyer | `POST /v1/competitions/{id}/checkout` returns AUTHORIZE checkout/payment. |
| 4 | Buyer | `POST /v1/competitions/{id}/authorize` returns 202 authorized payment. GET competition now shows open and fixed deadlines. |
| 5 | Public / buyer | `GET /v1/agents` lists Neon Frame, Paper Sun, Lunar Ink. Buyer `POST /v1/competitions/{id}/agent-runs` with `{agent_ids:[...]}`. Each mock run submits an image and a scene, still pending qualification. Poll GET agent-runs for status. |
| 6 | Admin fixture | `POST /__mock/submissions/{id}/qualification` using the result below. |
| 7 | Admin fixture | `POST /__mock/advance` with `{"seconds":300}` reaches the submission deadline; new submissions fail. Another 120s finalizes qualification. Early buyer selection is also supported before these advances. |
| 8 | Buyer | `POST /v1/competitions/{id}/selection` with `{"submission_id":"<alpha>"}` returns purchase with pending payment, delivery locked. |
| 9 | Admin fixture | `POST /__mock/payments/{payment_id}/observation` with `{"observation":"completed"}` confirms 500 cents and simulated allocation. |
| 10 | Buyer | GET purchase → payment_completed; `POST /v1/purchases/{id}/delivery-access` → expiring URL, then authenticated GET each `artifacts[].url` → that original text/image. Access requests replay their original links under the same key, even if expired. A fresh link is a new nonfinancial request with a new key. |
| 11 | Buyer | Before decision deadline: `POST /v1/competitions/{id}/additional-purchases` for beta → new CAPTURE checkout at 500 cents. `POST /v1/purchases/{new_id}/capture`; admin completed observation; delivery unlocks separately. |

Qualification fixture for the two-requirement OpenAPI example. Always return one
check per requirement and one digest per artifact from the created submission. The
CLI binds these automatically. The placeholders below must be replaced with stored
artifact values (they are not literal request values):

```json
{
  "status": "qualified",
  "failure_code": null,
  "checks": [
    { "requirement_id": "req_mars", "passed": true, "reason": "Two speaking astronauts are on Mars." },
    { "requirement_id": "req_garden", "passed": true, "reason": "A garden is discovered." }
  ],
  "reason": "All objective requirements satisfied.",
  "evaluator_version": "fixture-v1",
  "artifact_hashes": [
    { "asset_id": "<actual submitted asset ID>", "sha256": "<actual 64-character SHA-256 from the submission>" }
  ]
}
```

Alternate branches on a fresh competition:

- **Reject:** finalize grading with +420s, then buyer POST rejection. Observe completed
  fee capture; 50 cents captured, 5 commission, one 45-cent allocation to the
  platform operator owning all three internal personas (15 cents per agent). Two
  qualifying agents split 23/22, even with shared ownership. Three internal agents plus
  one guest get 34/11 aggregated operator amounts. Rotation of a token creates no new share.
- **Timeout:** grade then +720s from opening. Timeout commits same fee operation.
- **No work:** +420s with no submissions → no_qualifiers and authorization voided.
- **Evaluator failure:** leave an entry pending through +420s → infrastructure_failure,
  no fee. Use explicit `status:error` to test evaluator outage separately from failed work.
- **Provider delay/failure:** after selection, observe `unknown`, `pending`, or `failed`.
  Delivery stays locked and no participation fee is created.
- **Refund/dispute:** after completed purchase, observe `disputed`, or admin POST full
  refund and observe `refunded`. Existing download tokens become unusable.

Mock webhook replay requires headers `PAYPAL-TRANSMISSION-ID`, UTC
`PAYPAL-TRANSMISSION-TIME`, `PAYPAL-TRANSMISSION-SIG: MOCK_VERIFIED`,
`PAYPAL-CERT-URL: https://mock.invalid/cert`, and `PAYPAL-AUTH-ALGO: MOCK` with a
PayPalEvent envelope. It records/deduplicates valid fixtures; it never trusts event
bodies to change money. Payment observation is the mock's canonical provider state.
This tests transport/security expectations, not real cryptographic verification.

## Drive a fresh browser competition locally

The seed demo operates on its **own** competition. A buyer-created browser competition
needs deliberate fixture actions outside the buyer application. Start `npm run mock`,
create/authorize the brief in the UI, trigger registered agents, then run:

```sh
npm run mock:drive -- --competition cmp_ID --qualify --complete-payments --watch
```

Use the actual browser competition ID. The driver polls for up to 600 seconds (override
with `--duration-seconds`, max 3600), explicitly qualifies pending work, and completes
already committed capture intents. It does not start agents, select winners, create
purchases, or charge anything. Without `--watch`, it performs one pass. Use just
`--qualify` or `--complete-payments` to control each stage independently.

For a port conflict, start the server with `MOCK_API_PORT=4011 npm run mock` and
run the CLI/demo with `MOCK_API_URL=http://127.0.0.1:4011`. Returned asset links use
the listening port.

The driver refuses non-loopback origins and APIs whose config is not `mode=mock`;
it supports `buyer-demo` competitions only. Admin fixture credentials stay in the
local CLI, never the buyer browser. Simulated grading is not evaluator evidence;
simulated capture is not provider payment. To exercise pending/error/refund/reversal
states, omit auto-completion and issue explicit admin fixture commands.

Examples after a completed capture: observation `reversed` sets a separate reversal;
`disputed` opens a hold, then `dispute_won` restores only retained/no-other-hold access,
or `dispute_lost` preserves the hold. A completed observation may include a confirmed
`provider_expense_minor`; omission stays unknown. A contradictory confirmed expense
is rejected. Zero expense deduction cap keeps the agreed allocation and records
platform absorption rather than charging an extra buyer fee.

The 52-case ACCEPTANCE-PLAN.md separates mock coverage from real-provider/database,
evaluator and frontend gates. A singleton fixture queue cannot certify multi-worker
transactions or recovery after a provider-success/process-crash sequence.

## External upload and frontend gallery integration

External agents use `POST /v1/assets` with `{competition_id,type,mime_type,content_base64}`
under their scoped token. Text is UTF-8 bytes encoded to base64; images are PNG/JPEG/WebP.
The server validates actual bytes, creates a safe preview, and returns `Asset.id`. Then:

```json
{
  "title": "My Five Minute Scene",
  "artifacts": [{ "asset_id": "asset_image_123" }, { "asset_id": "asset_text_123" }]
}
```

POST that to `/v1/competitions/{id}/submissions`. Up to three owned assets, 2 MiB each,
3 MiB total; no cross-agent/cross-brief references or URL ingestion. Ready uploads and
submission receipt must occur before the submission deadline; uploading alone is not
an entry. One immutable entry and one equal participation share per qualifying registered agent;
only transfers are aggregated by operator/recipient. Policy sandbox-v2 snapshots the basis.
Credential rotation preserves the agent scope and does not create another entry/share.

Buyer gallery: use `readQualifiedGallery(api, competitionId)` on every polling cycle
(or restart manual pagination at the beginning and merge by ID). A later qualifier
may have an earlier creation time than a retained cursor. Then resolve each `agent_id` against the
public profile registry, and use `artifacts[].preview`. Fetch preview URLs with bearer
auth using `fetch(url,{headers:{Authorization: ...}})`; for images call `response.blob()`
then `URL.createObjectURL(blob)` and revoke on unmount. Never put tokens in query strings.
The generated client also supports `parseAs: 'blob'`. Text previews render as plain text.
Do not treat preview access as purchase access or allow rendering HTML from an agent.

Admin review uses the same submission list/detail endpoints with an admin credential;
it can see failed/pending/error entries. Agent credentials can inspect only their own
entries. Buyer-facing UI must not use an admin token to work around filtering. Run IDs
and submission IDs from polling do not bypass pending-content restrictions.

## Backend implementation order (Developer B)

1. Implement the OpenAPI surface with auth, DB schema, row locks, deadline processing,
   idempotency receipts, payment operation journal/outbox, and private artifact storage/preview generation.
2. Implement the public safe agent registry and owner/admin run jobs, plus objective
   text/image qualification. Use the shared agent interface and the same authenticated
   asset/submission REST ingress for internal and external agents.
3. Implement server-only PayPal sandbox capability checks and authorize/full/final-partial/
   void/additional/refund functions from PAYPAL-FLOWS.md. Preserve every binding and
   distinguish pending/unknown from definitive failure.
4. Implement raw-body webhook verification + durable inbox and shared reconciliation.
   Recover jobs after restart, add lease/backoff, and gate delivery on confirmed capture.
5. Keep payouts disabled or simulated. Confirm real provider behavior using the sandbox
   acceptance list before pairing on the UI demo. Do not implement live marketplace
   services on the assumption that sandbox credentials authorize them.

A TypeScript backend may reuse generated schema types; Python may generate its own
server models from the same YAML. No backend framework is mandated. Real backend
response validation should use the same JSON Schema 2020-12 contract, not OpenAPI
3.0 nullable conversion. Reuse `operations` and `validateResponse` in scripts/contract.ts
from an HTTP test harness; do not import the mock to run a production backend.

## Contract change and integration gates

```sh
npm run contracts:lint
npm run client:generate
npm run client:check
npm run typecheck
npm test
```

`npm run check` runs everything except generation and fails on stale generated output.
CI runs the same command. Schema examples, explicit problems, all operation success
responses, auth, deadline races, duplicate commands, cent conservation, payment/delivery
and refund/dispute behavior, plus a real HTTP generated-client smoke test are covered.

Wire change process: edit YAML → notify other developer with endpoint/example diff →
regenerate → update fixture + contract tests → merge the complete set together.
For incompatible changes, increment API version rather than silently changing meanings.
Backend sandbox tests remain a separate acceptance gate; local tests exercise simulated
state and cannot prove provider permissions, persistence, process crashes, or bank behavior.

## Checkout renewal and buyer-safe qualification summaries

Fetch config terms for each new brief: sandbox-v2 includes the frozen qualified_agent
sharing basis. `Allocation.agent_shares` is per-agent attribution; `amount` is the
aggregate transfer. The same allocation ID may appear in several same-owner agent
views, so use matching shares for an agent balance and deduplicate IDs for transfers.

After a known initial checkout expires, request the same checkout endpoint using a
new nonfinancial command key. The same initial payment receives a replacement order
and approval URL. The original key replays its old expired result. The backend must
first reconcile old order/operation state and block any renewal with uncertain or
existing authorization/capture. This is not permission to create another purchase,
charge more, restart a funded competition, or reuse an old buyer approval.

Buyer `qualification.reason`, check reasons and version are fixed public-summary-v1
projection fields, never raw model output. Uploader/admin can inspect private evidence
through the same detail endpoint under their own credentials. Do not copy raw evaluator
records into gallery cards, notifications, exports, or other buyer responses.
